# Spec A — EIP-1559 transaction type

## Goal
Add support for EIP-1559 (type-2) transactions alongside the existing legacy `EvmTransaction`. The toolkit today only expresses legacy `gasPrice`-style transactions; all live EVM chains we target (Ethereum, Base, Polygon, Arbitrum) expect EIP-1559 fees by default.

This is an **EVM data model + serialization** task. It does **not** touch signing — signing still delegates to Trust Wallet Core, which already handles both tx types when given the right JSON.

## Module(s) touched
- `wallet-evm` — only.
- `wallet-core` — **not touched**. If you find yourself needing to edit `EvmTransactionData`, stop and raise it.

## Files expected to change
- `wallet-evm/src/commonMain/kotlin/xyz/wallet/toolkit/evm/Eip1559Transaction.kt` (new)
- `wallet-evm/src/commonMain/kotlin/xyz/wallet/toolkit/evm/EvmSigningPayload.kt` (extend with a `toSigningPayload()` for the new type — do **not** break the existing overload)
- `wallet-evm/src/commonTest/kotlin/xyz/wallet/toolkit/evm/Eip1559SigningPayloadTest.kt` (new)
- `wallet-evm/src/commonTest/kotlin/xyz/wallet/toolkit/evm/Eip1559GoldenVectorTest.kt` (new — see acceptance criteria)

No changes to `EvmTransaction.kt`. No changes to anything outside `wallet-evm`.

## Design
- New data class `Eip1559Transaction` in `xyz.wallet.toolkit.evm`, `@Serializable`, parallel to `EvmTransaction`. Fields:
  - `chainId: Long`
  - `to: String`
  - `valueWei: String = "0"`
  - `maxFeePerGasWei: String`
  - `maxPriorityFeePerGasWei: String`
  - `gasLimit: String`
  - `nonce: Long`
  - `dataHex: String? = null`
  - `accessList: List<AccessListEntry> = emptyList()` — where `AccessListEntry(address: String, storageKeys: List<String>)`.

- `Eip1559Transaction` does **not** implement `EvmTransactionData`. The existing `EvmTransactionData` interface is shaped around legacy `gasPriceWei` and adding optional fields to it would force every consumer to care about fee model. Keep it parallel, not subtyped. (If the planner disagrees, it must say so in the plan and surface to the user — do not silently change `EvmTransactionData`.)

- `fun Eip1559Transaction.toSigningPayload(json: Json = Json): ByteArray` encodes to the canonical JSON shape that the Trust Wallet Core signing bridge will understand. Field ordering and naming must be deterministic — use the explicit `@Serializable` data class, not a dynamic `JsonObject { ... }` builder.

## Acceptance criteria

A task is **not done** until every one of these passes.

1. `./gradlew :wallet-evm:allTests` — green.
2. `./gradlew :wallet-evm:compileKotlinJvm` — green.
3. Round-trip serialization test: an `Eip1559Transaction` with all fields populated (including a two-entry access list) serializes to JSON and deserializes back to an equal instance.
4. Field-ordering test: the serialized JSON's key order for the standard case (no access list, no data) matches a hardcoded expected string byte-for-byte. If Kotlin serialization changes default ordering, this test catches it.
5. **Golden-vector test** (`Eip1559GoldenVectorTest`): given a fixed `Eip1559Transaction` with the exact values below, `toSigningPayload().decodeToString()` produces the exact JSON string stored in the test. The expected string must be committed; the test asserts string equality.
   - chainId = 1, nonce = 42, to = "0x3535353535353535353535353535353535353535", valueWei = "1000000000000000000" (1 ETH in wei), maxPriorityFeePerGasWei = "1000000000", maxFeePerGasWei = "50000000000", gasLimit = "21000", dataHex = null, accessList = [].
   - The expected JSON string is not yet in the spec; the implementer generates it **once** with the first passing implementation, inspects it manually, and commits it. Subsequent runs must match. This protects against accidental serialization drift.
6. Legacy `EvmTransaction` tests still pass unchanged. Diff the legacy test file — it should have zero changes.
7. No `EvmTransactionData` consumer was modified.
8. No file outside `wallet-evm` was modified.

## Non-goals
- Signing. The signing path will pick up the new JSON once it's fed in. Do not edit the Trust Wallet Core bridge.
- RLP encoding. We serialize to JSON; TWC does the RLP.
- `accessList` RLP compliance or address checksum validation — JSON pass-through is enough for this task.
- A new chain entry in `ChainRegistry`. EIP-1559 is orthogonal to chain identity.
- Sample app updates.

## Why this is interesting for the experiment
- Pure commonMain, zero platform coupling — baseline for "how well does the agent do when there are no KMP hazards in its way".
- Serialization drift is a classic silent-failure mode for signing code; the golden-vector requirement tests the agent's discipline around CLAUDE.md §4 rule 8.
- File-disjoint from spec B — safe to run in parallel.
