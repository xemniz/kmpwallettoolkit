# Plan — Spec A: EIP-1559 transaction type in wallet-evm

## Summary

Add an `Eip1559Transaction` data class and a parallel `toSigningPayload(...)` extension in `wallet-evm`, leaving the existing legacy `EvmTransaction` untouched. The spec's approach — a **sibling** type that does **not** implement `EvmTransactionData` — is reasonable: the legacy interface is shaped around `gasPriceWei`, and EIP-1559 replaces that with a max-fee pair. Subtyping would force fee-model concerns onto every legacy consumer. Treat the two types as siblings, identical pattern, disjoint fields.

This is pure commonMain work. No platform code, no new deps, no `expect/actual`, no changes outside `wallet-evm`.

### Phase 1 — Data model + minimum serialization, green tests

1. Create `Eip1559Transaction.kt` with:
   - `@Serializable data class AccessListEntry(val address: String, val storageKeys: List<String>)`.
   - `@Serializable data class Eip1559Transaction(chainId, to, valueWei="0", maxFeePerGasWei, maxPriorityFeePerGasWei, gasLimit, nonce, dataHex=null, accessList=emptyList())` with types exactly as in the spec's "Design" section. Property order in the source file defines JSON key order for the default `Json` instance; use the order from the spec: `chainId, to, valueWei, maxFeePerGasWei, maxPriorityFeePerGasWei, gasLimit, nonce, dataHex, accessList`.
   - Trailing commas on multi-line parameter lists (CLAUDE.md §5).
   - No KDoc unless an invariant is non-obvious (§5).
2. In `EvmSigningPayload.kt`, add `fun Eip1559Transaction.toSigningPayload(json: Json = Json): ByteArray = json.encodeToString(this).encodeToByteArray()`. Keep the existing legacy extension byte-for-byte. Add the required `import kotlinx.serialization.encodeToString` only once (already present).
3. Create `Eip1559SigningPayloadTest.kt` with two tests initially:
   - **Round-trip**: build an `Eip1559Transaction` with **every** field populated (non-null `dataHex = "0xdeadbeef"`, a two-entry access list with distinct addresses and at least one storage key each), serialize via `Json.encodeToString`, deserialize via `Json.decodeFromString`, assert `decoded == original`.
   - **Field-ordering smoke**: for the simple case (no `dataHex`, empty `accessList`), assert the serialized JSON string `startsWith("{\"chainId\":")` and that the substring `"\"nonce\":"` appears after `"\"gasLimit\":"`. This catches accidental reordering without duplicating the golden vector.
4. Run `./gradlew :wallet-evm:allTests`. Gate: green.

3. Paste the inspected string verbatim into `EXPECTED_JSON` (escape double quotes). Remove the `println` / unwire the debug path. Commit as part of Phase 2.
4. Run `./gradlew :wallet-evm:allTests`. Gate: green. Any subsequent serialization change flips this test red — that is the feature.

## Golden vectors

Spec A is deliberately different from the usual signing-test pattern. There is **no upstream authoritative vector** for this JSON shape because the JSON is an internal contract between `wallet-evm` and the Trust Wallet Core signing bridge — not a standardized wire format. The vector is a **drift guard**, not an interop proof. This satisfies CLAUDE.md §4 rule 8 (serialization change → golden test) while honoring rule 5's intent: the test is not worthless because it pins exact bytes, but it pins them to a locally-chosen canonical form rather than an external reference.

**Input (verbatim from spec §Acceptance §5):**

| Field | Value |
|---|---|
| `chainId` | `1` |
| `nonce` | `42` |
| `to` | `"0x3535353535353535353535353535353535353535"` |
| `valueWei` | `"1000000000000000000"` (1 ETH) |
| `maxPriorityFeePerGasWei` | `"1000000000"` |
| `maxFeePerGasWei` | `"50000000000"` |
| `gasLimit` | `"21000"` |
| `dataHex` | `null` |
| `accessList` | `[]` |

**Procedure:**
1. First implementation run produces a JSON string. Implementer inspects it manually for the things called out in Phase 2 step 2.
2. Implementer commits the inspected string into `Eip1559GoldenVectorTest.kt` as `private const val EXPECTED_JSON = "..."`.
3. From then on, the test asserts byte-for-byte equality. Any serialization-affecting change (field reorder, default handling, encoding of nulls, `accessList` empty-array emission, wei-as-string semantics) flips this test red and forces a deliberate re-inspection.

**No interop vector is introduced for signing output**, because spec A explicitly does not touch signing.

## Crypto hygiene — CLAUDE.md §4 applicability

Most of §4 is orthogonal to this task (no entropy, no key material, no HMAC comparisons, no nonces from PRNGs). The rules that **do** apply:

- **§4.8 Serialization of transactions is security-relevant.** This plan's Phase 2 golden-vector test is the direct response. Without it, a later refactor (adding a field, changing kotlinx-serialization's `Json` defaults, moving to `Json { encodeDefaults = false }`) could silently change the signing input.
- **§4.6 Never weaken an existing assertion to make a test pass.** If the golden test goes red after an unrelated change, the fix is to re-inspect and decide whether the new output is intentional — not to regenerate the expected string blindly. Phase 2 commits the string *after* human inspection; Phase 4 and onward treat it as locked.
- **§4.1 Never log or `toString` sensitive material.** Neither `Eip1559Transaction` nor `AccessListEntry` holds a private key or mnemonic — they hold transaction metadata, which is public by construction. Default `toString()` is acceptable. Do **not** add `toString` overrides that redact these fields; that would be cargo-culted hygiene and would hurt debuggability.
- **§4.7 Don't compare addresses case-sensitively.** Not triggered by this task (we're doing JSON pass-through, no address equality checks). Out of scope per spec Non-goals.

Rules §4.2, §4.3, §4.4, §4.5 — not applicable to this task (no randomness, no secret comparisons, no nonces generated locally, no signing).

## Risks / Open questions

1. **`encodeDefaults` behavior.** Default `Json` emits properties whose value equals the declared default (e.g., `valueWei = "0"`, `accessList = []`). Confirm on the first Phase 2 run that the golden JSON contains these defaulted fields. If `encodeDefaults = false` is ever needed, the `Json` instance at the call site — not the class — must change, and the golden test will enforce that decision. No action needed now; just be aware during Phase 2 inspection.
2. **`dataHex = null` rendering.** Kotlinx serialization by default encodes `null` for nullable properties (unless `explicitNulls = false`). The expected golden JSON should contain `"dataHex":null`. Inspector must confirm this during Phase 2. If the team later prefers to omit nulls, that is a deliberate JSON-contract change and should flip the golden test.
3. **TWC expected shape.** The Trust Wallet Core signing bridge's contract for the new type is not specified here. Spec A explicitly defers signing to a follow-up. The golden test pins the output to *our chosen* shape, not TWC's. When signing is wired up in a later task, expect to revise the golden JSON and the field names to match TWC's exact JSON schema for EIP-1559 (e.g., TWC may expect `chainID` vs `chainId`, `maxFeePerGas` vs `maxFeePerGasWei`, `storageKey` vs `storageKeys`). **Do not try to guess TWC's shape in this task.** This is explicitly out of scope (spec Non-goals). Flagging so the implementer does not over-reach.
4. **`AccessListEntry` placement.** The spec asks for it in `xyz.wallet.toolkit.evm`. Two choices: declare it as a top-level class in `Eip1559Transaction.kt`, or nest it. Recommend top-level in the same file — easier to reference from tests, still file-disjoint from anything else. No separate file needed; this is a single data class pair with a tight invariant coupling.
5. **Legacy `EvmSigningPayloadTest` coincidental breakage.** Adding a second `toSigningPayload` extension in the same file creates an overload set. The legacy test imports the extension via whole-package resolution (`tx.toSigningPayload()`), which stays unambiguous because the receiver types differ. No legacy diff should be needed; if Kotlin resolution complains, stop and raise — do not edit the legacy test (spec acceptance #6).
